# 阶段 B 报告：口语症状按白名单归类

> 前置：`reports/uplift-baseline.md`（阶段 A）｜ 检查点：`v6-hard-eval` → 本报告 → `v7-llm-symptom`
> 日期：2026-11-18 ｜ 题集：`data/eval/questions_hard.jsonl`（20 题）× 3 次重复

---

## 1. 改了什么（一行核心改动）

`decompose_prompt` 里 `symptom` 的规则，从

> 现象/症状名（如「左轮不转」），**用问题原文措辞**；没有就 null

改成

> 从【图谱症状清单】里选语义最贴近的一个，**原样输出该名称**；清单里没有接近的置 null，不要自造症状名

并在提示词里附上 28 个症状名。**没有动推理内核、没有动 `_guard_answer`、没有新增工具。**

为什么这一行能起作用：`_merge_slots` 拿到 LLM 的症状后要 `store.search(symptom, label="Symptom")`
才能命中节点。原文措辞（「支架老是掉」）搜不到标准名（「拖布支架松动」），等于没抽到；
改成从清单里选，等于把「生成题」变成「28 选 1 的分类题」，命中率从 0/5 变成 5/5。

这同时是降幻觉措施：LLM 不再产出图谱外的症状名，编造实体的入口被这一条堵住。

## 3. H1–H5 判定

| 编号 | 标准 | 实测 | 判定 |
|---|---|---|---|
| **H1** | McNemar 双侧 p<0.05 且 c=0 | 答案准确率：b=6 c=0 **p=0.0312** ／ 首选方案：b=5 c=0 **p=0.0625** | ⚠️ **部分通过** |
| **H2** | 编造/悬空仍为 0 | 0 / 0 | ✅ |
| **H3** | 安全违规仍为 0 | 0 | ✅ |
| **H4** | 原 50 题不下降（≥0.980） | **0.980**（唯一错题仍是 Q028），首选方案 0.7907 | ✅ |
| **H5** | 闸门拒绝率有记录 | **不适用**：本阶段未做事实抽取，无闸门 | — |

### H1 为什么只能算部分通过

两个口径差一个样本：

- 用答案准确率（20 题全参与）：6 题翻盘、0 题退步，双侧 **p = 0.0312**，通过。
- 用首选方案（只有 15 题有方案金标准）：5 题翻盘、0 题退步，双侧 **p = 0.0625**，不通过。

按阶段 A 确立的口径（首选方案才是「推荐了什么」的正确度量），**主判据应取后者**，
即 **H1 未通过**。答案准确率的 0.0312 只在「提到过正确答案」这个较松的意义上成立。

**结论：阶段 B 有真实收益，但按最严判据尚未达到统计显著。** 差的那一题是 H12
（「自己回不去、在客厅转来转去找不到路」）——症状抽对了（乱走迷路），但答案没有把
「清洁雷达视窗」作为首选，而是给了竞态解释。

### 一致性下降 5 pp，必须记下来

`exactRepeatRate` 0.95 → 0.90，不稳定题从 1 个（H07）变成 2 个（H05、H07）。
原因不是随机：症状抽对之后，后续要跑更多工具、答案更长，LLM 在同样 temperature=0 下
的措辞分化更明显。这不是精度问题，但会影响「同一问题两次问得到不同说法」的体验。

Pass^3 反而上升（0.60 → 0.85），说明**答对更稳定了，答法更不稳定了**——这两个是不同的事，
不能用一个数概括。

## 5. 剩余缺口：`precondition` 8 题，首选方案 0/8

这 8 题的共同结构是「用户已经做了某件事，而系统仍按默认顺序推荐那件事」：

| 题 | 用户说的 | 系统推荐的 |
|---|---|---|
| H01 | 毛发清理干净了还是卡 | 清理轮组缠绕物 |
| H03 | 刷毛清理干净了 | 清理边刷 |
| H04 | 触点用酒精棉擦过了 | 清洁充电触点 |
| H06 | 清水箱重装过好几次 | 重新安装清水箱 |
| H08 | 滤网上周刚换新的 | 更换滤网 |

要修它，必须让「已做过」变成规则引擎能消费的事实。两条路：

**路 A（原计划，需动内核）**：LLM 抽 `check_results` → 新增规则 R25「阴性结果排除该根因」
→ `_assemble` 剔除被排除根因后重排。
代价：动 `facts.py` / `rules.yaml` / `service.py` 三处，涉及根因层的新谓词 `reject_cause`，
现有 143 条测试要全绿，风险中等。

**路 B（不动内核，在 Agent 层重排）**：LLM 抽「用户已做动作」→ Agent 在拿到 `Diagnosis` 后，
把与「已做动作」对应的方案降权或剔除，再重排。
代价：改 `graph.py` 的组装逻辑，规则引擎不变。
风险：结论不再完全由规则产出，审计链变长；需要额外记录「为什么降权」。

**建议走路 A**，理由：它保持了「结论由规则引擎产出」这条审计线，
而路 B 会让「同一个症状两次问出不同首选方案」变得难以解释。这也是提升计划最初的设计取向。

但路 A 必须单独做一轮，且要有自己的验收标准——见 §6。
