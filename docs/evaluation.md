## 2. 五组系统

| 组 | 名称 | 配置 | 目的 |
| --- | --- | --- | --- |
| A | `rule` | 规则引擎 + 实体链接，确定性，不调 LLM | 确定性基线 |
| B | `rag` | 取最强一条 症状→故障→根因→方案 链，单轮模板回答 | 常见「LLM + KG」下限 |
| C | `agent` | 查询解耦 + 工具探索 + 反思 + 规则校验 + 证据重建 | 本文方法 |
| D | `agent_noreflect` | C 去掉 reflect 节点（`use_reflection=False`） | 消融：反思 |
| E | `agent_norules` | C 把 `run_rules` 换成 `retrieve_chain`，只走图检索链（`use_rules=False`） | 消融：规则 |

公平性控制：

- 同一图谱快照（410 实体 / 954 关系）、同一评测集、同一评分脚本；
- 同一台机器、同一后端（Neo4j 2025.07，单机）；
- 每组跑 3 次报均值 ± 标准差——本实现不调 LLM，标准差预期为 0，
  跑 3 次是为了把「可复现」从口头声明变成可核对的数字。

> 关于「不调 LLM」：这是刻意的取舍。接入 LLM 后同一题两次运行可能给出不同证据链，
> 而本项目的核心指标（Path F1 / Faithfulness）恰恰依赖证据链稳定。
> 所以 LLM 只作为后续可替换件（`backend/app/llm/` 预留），不进主实验。

## 3. 评测集

`data/eval/questions.jsonl`，50 题，`split=test`。题面全部是自然语言，金标准含
`goldFaults` / `goldSolution` / `goldEvidenceTriples` / `mustInclude` 四类标注。

| 题型 | 题数 | 例子 | 考什么 |
| --- | ---: | --- | --- |
| `single_hop` | 10 | T20 PRO 报 E11，左轮不转 | 实体链接 + 一跳推理 |
| `two_hop` | 11 | 报 E11，应该先做哪一项检查？ | 故障 → 根因 → 检查 |
| `multi_hop` | 13 | 清理轮组后还是卡，是不是要换轮组？ | 3~4 跳 + 前提条件 |
| `ambiguity` | 5 | 报 E15，是风机坏了还是滤网堵了？ | 多候选不下单一结论 |
| `model_scope` | 4 | T10 TURBO 报 E13 是什么？ | 型号未收录的降级 |
| `safety` | 4 | 电池鼓包了还能继续用吗？ | 安全拦截 |
| `out_of_scope` | 3 | 窗宝怎么擦玻璃？ | 范围外拒答 |

**分母说明**：50 题里 7 题（型号未收录 4 + 超范围 3）本来就没有故障/方案/证据可答，
不参与 `faultF1` / `solutionAcc` / `path*` 三项均值，实际计分 **43 题**（结果里的 `nFaultScored`）。
把它们按 0 分计入，会让整体指标被无解题系统性压低约 14%——
「系统答错了」和「题目没有答案」是两件事，指标不能混。

## 4. 指标

| 指标 | 计算口径 | 对应代码 |
| --- | --- | --- |
| Answer Accuracy | 答案文本包含全部 `mustInclude` 关键词 | `metrics.answer_correct` |
| Fault F1 | 候选故障集合与 `goldFaults` 的 F1 | `metrics.fault_prf` |
| Solution Accuracy | 前 3 个方案里有命中 `goldSolution` | `run_eval` |
| Path P / R / F1 | **证据三元组集合**的 P/R/F1，不比节点序列 | `metrics.path_prf` |
| Faithfulness | 带 `evidenceId` 的 claim / 总 claim | `metrics.faithfulness` |
| Hallucination | 无 `evidenceId` 的 claim 占比 | `metrics.hallucination_rate` |
| Coverage | Agent 五个子问题中 `covered` 的比例（A/B 组无此环节，记 `—`） | `run_eval._run_agent` |
| Tool Calls | 平均工具调用次数（循环率 = 重复调用/总调用，见 trace） | 同上 |
| Latency | P50 / P95 端到端时延 | `metrics.percentile` |

Path 指标按**三元组集合**算而不是按节点序列，因为同一路径有多种合法写法
（`SYM:X → FAULT:Y` 与 `FAULT:Y ← SYM:X` 是同一件事），按序列比会把写法差异算成错误。

## 6. 怎么读这张表

### 6.1 路径指标必须 P/R 一起看

规则/Agent 输出的是**完整证明链**（召回 0.942），分母大所以精度被摊薄到 0.237；
弱基线只返回一条最短路，精度反而更高（0.267）但漏掉了 2/3 的必要证据（召回 0.333）。

只看 F1 会得出「检索比推理更好」的错误结论——这是路径类指标最典型的误读方式。
所以在报告里 P 和 R 必须并排出现。

### 6.2 弱基线不会说「不知道」

B 组的答案准确率只有 0.300，35 题错，分布是这样的：

| 错误题型 | 题数 | 原因 |
| --- | ---: | --- |
| 两跳 / 多跳 | 21 | 只走一条链，跳不到「检查项」与前提条件 |
| 型号范围 | 4 | 型号未收录也照答，不降级 |
| 超范围 | 3 | 问窗宝也答扫地机，不拒答 |
| 歧义 | 4 | 只取 top-1 故障，不保留多候选 |
| 安全 | 3 | 无安全拦截 |

它的 `faultF1` 高达 0.946——因为故障名基本能猜对。**只看 faultF1 会严重高估它的能力**：
它猜对了病名，但开错了药（不给检查，直接给方案），并且在四个用户问「我这型号有没有这功能」的
场景里编答案。答案级与路径级指标才是区分点。

### 6.3 规则与 Agent 在准确率上持平，增益在上下文

A 与 C 的答案级指标完全一致——因为它们**共用同一个推理内核**，Agent 不是另一个更聪明的模型，
而是在同一份证据上加了一层编排。C 的增益体现在：

- `coverage` 0.915：五个子问题里有 91.5% 被证据覆盖，缺的那部分会**主动说明**（「未检索到相似案例」）；
- 2.06 次工具调用换来「相似工单 / 耗材兼容性 / 覆盖度自检」三块上下文；
- 代价是时延从 317ms 涨到 698ms。

### 6.4 为什么 Agent 时延比规则高 2 倍

不是因为工具调用多（只多 2 次），而是因为规则层的事实投影要扫全图（`rules/facts.py` 遍历
`Fault` 节点与兼容性矩阵），每跳一次 Neo4j 一次往返。可优化项（缓存事实投影、批量取邻居）
已记在 §9，本轮没做——先把正确性做对，再谈速度。

## 7. 消融

### 7.1 D：去掉反思（C → D）

| 指标 | C | D | 变化 |
| --- | ---: | ---: | ---: |
| Answer Acc | 0.980 | 0.980 | 0 |
| Path R | 0.942 | 0.942 | 0 |
| Coverage | 0.915 | 0.889 | **-0.026** |
| 工具调用 | 2.06 | 1.94 | -0.12 |

**诚实的结论：反思在本实验里几乎没有用。** 50 题里有 6 题的覆盖度因为关掉反思而从 1.0 掉到 0.8
（Q007 / Q015 / Q018 / Q020 / Q034 / Q046），且掉的都是同一格：`q3` 相似案例。
故障、根因、方案的证据链没有变化——答案文本的区别只是多了一句
「图谱中未检索到同型号的相似案例，结论仅基于知识链与规则」。

原因有两层：

1. **兜底计划已经足够强**：`plan` 一开始就调用了 `run_rules` 且直接覆盖 365 天窗口，
   留给反思的空间只剩「同型号全症状」这一级放宽；
2. **反思目前只会补「上下文」，不会补「证据」**：它会调 `expand_subgraph`，
   但扩展出来的子图不进诊断证据集，所以 Path 指标不可能变化。

这不是「反思无用」的普适结论，而是「在这个图谱规模 + 这个确定性规划器下，反思没有可发挥的余地」。
要让反思真正起作用，需要两件事同时成立：图谱更大（单链到不了目标）、
以及反思动作能新增证据边（例如多跳路径检索后把新路径并入证明）。
后者是明确的改进项，写进 §9。

### 7.2 E：去掉规则（C → E）

| 指标 | C | E | 变化 |
| --- | ---: | ---: | ---: |
| Answer Acc | 0.980 | 0.800 | **-0.180** |
| Path R | 0.942 | 0.872 | -0.070 |
| Path F1 | 0.370 | 0.323 | -0.047 |
| Faithfulness | 0.804 | 0.845 | +0.041 |

10 题退化，按题型分：

| 题型 | 题号 | 退化原因 |
| --- | --- | --- |
| 多跳 / 两跳 | Q019 Q022 Q024 Q026 | 没有规则加权与检查排序，根因退回「边置信度最高者」，选成次要根因 |
| 歧义 | Q036 Q037 | 歧义题需要按鉴别性检查选主候选，无规则时并列并列输出 |
| 安全 | Q044 Q046 Q047 | 无 `safety_stop` 策略，安全告警与停用建议整体消失 |
| 多跳（本来错） | Q028 | 两组都错，见 §8 |

Faithfulness 反而升高（0.845 > 0.804）的原因值得单说：E 组的 claim 更少
（没有安全拦截这条 `evidenceIds=[]` 的 claim），所以「有证据的比例」被动变高。
**这说明 Faithfulness 不能单独用**——一个什么都不说的系统 faithfulness 天然是 1.0。
它必须和 Answer Acc 一起看：E 组是用「少说话」换来的高 faithfulness。

这个消融是本项目最有说服力的一组：它证明规则层不是「给结论加点解释」的装饰，
而是直接决定结论正确性的部件——尤其是在安全场景（3 题全错）与多候选歧义场景（2 题错）。

## 8. 误差分析

### 8.1 错误分类计数

错误类型沿用文档 9.6 的分类。

| 错误类型 | A rule | B rag | C agent | D | E |
| --- | ---: | ---: | ---: | ---: | ---: |
| Entity Linking | 0 | 0 | 0 | 0 | 0 |
| Missing Edge | 0 | 21 | 0 | 0 | 0 |
| Retrieval Noise | 0 | 0 | 0 | 0 | 0 |
| **Rule Gap** | **1** | 4 | **1** | **1** | **7** |
| Over-reasoning | 0 | 0 | 0 | 0 | 0 |
| Unsupported Claim | 0 | 7 | 0 | 0 | 0 |
| Conflict Handling | 0 | 0 | 0 | 0 | 0 |
| Safety Failure | 0 | 3 | 0 | 0 | **3** |
| 合计错题 | 1 | 35 | 1 | 1 | 10 |

两点值得注意：

- **Entity Linking 0 错**：50 题的型号/错误码/症状全部链接正确。这不是运气——
  错误码按「型号 × 错误码」建键，`E11` 不会串到别的型号；槽位抽取对「中文紧邻字母」
  （`T20 PRO的E11`）做了 lookaround 处理，有专门的回归测试。
- **Missing Edge 只在弱基线上出现**：不是图缺边，而是它只走一条链，走不到第二跳。
  这类错误归给「检索策略」而不是「图谱质量」更准确。

### 8.2 案例一：Q028（规则/Agent 都错）——缺「已执行动作」这个事实

**题面**：`T20 PRO 报 E11，清理轮组后还是卡，是不是要换轮组？`
**金标准**：首要根因应为「轮组轴承磨损」，答案须含「轮组轴承磨损」。

系统输出：

> 最可能的故障是「左驱动轮卡滞」（置信度 0.82）…首要根因推断为「轮轴毛发或线材缠绕」（0.75）。

Trace 显示：`CAUSED_BY` 两条边都被读到（毛发 0.75 / 轴承磨损 0.45），规则 R05 正常触发，
但没有一条规则知道「用户已经清理过」——**图谱里没有「已执行动作」这类事实**，
于是「先清理毛发」这个默认推荐顺序仍然生效。

**修正建议**（不改图谱也能做一半）：在槽位层识别「已做过 X」的完成态描述，
投影成事实 `action_done(symptom, clean_wheel)`，加一条规则：

```yaml
- id: R25
  name: 已执行动作排除对应根因
  when:
    - (case, observed, symptom)
    - (cause, resolved_by, solution)        # 该根因的处置方案 = 用户已做的动作
    - action_done(case, solution)
  then:
    - (cause, excluded, true)
```

这条规则同时能修「已重启路由器还让重启」这类同型问题——都属于「图谱缺时间/动作维度」，
是本体设计层面的缺口，不是调参能解决的。

### 8.3 案例二：Q044（E 组错）——规则是安全边界的唯一守门人

**题面**：`电池鼓包了还能继续用吗？`
**金标准**：答案须含「停止使用」。

| 组 | 输出开头 | 是否含安全告警 |
| --- | --- | --- |
| C `agent` | 最可能的故障是「电池过热或鼓包」… ⚠️ 该症状属于安全风险，请先停止使用并断开充电 | ✅ R14 触发 |
| E `w/o rules` | 最可能的故障是「电池过热或鼓包」… 建议按顺序检查：电池外观安全检查… | ❌ |

E 组甚至给出「感受电池区域温度」这种在鼓包场景下应当被禁止的动作。
这题的失败不是「答得不够好」，而是**给出了危险建议**——这也是为什么安全规则必须是硬拦截，
不能交给「模型判断」或「按置信度排序」。

### 8.4 案例三：Q011（B 组错）——猜对病名，开错药

**题面**：`T20 PRO 报 E11，左轮不转，应该先做哪一项检查？`
**金标准**：须含「轮轴毛发」「手动转动左轮」。

B 组输出：

> 检索到最相关故障：左驱动轮卡滞。建议方案：清理轮组缠绕物。

故障名对了（`faultF1` 满分），但它**跳过了检查直接给方案**，而题面问的正是「先做哪项检查」。
这条链在 `Cause → Check` 处断开，Path F1 只有 0.5。

弱基线的失效模式高度一致：**结构上少一条边，语义上就少一个前提**。
用户拿到「清理轮组」这条建议，不知道该怎么判断到底是不是毛发——
到了售后环节，这就是一次无效上门。

## 9. 已知局限与改进项

| 局限 | 影响 | 改进 |
| --- | --- | --- |
| 单机型语料（T20 PRO） | CQ7 跨型号比较、跨型号评测题不可做；`model_scope` 4 题只能考降级 | 补抓 T10/T30 语料，抽取层已不绑定型号 |
| 真实 FAQ 未批量进图 | 图中 FAQCase 是模板代理，`verbatim` 边为 0 | 走「候选 → 审核 → 进图」，见 `docs/extraction.md` §4 |
| 反思只补上下文不补证据 | D 组消融接近零效应 | 让反思把多跳路径并入证明子图，Path 指标才会动 |
| 事实投影每次全图扫描 | Agent P50 698ms | 缓存投影 + 批量取邻居 |
| 可解释性未做人工评分 | 缺 Explainability Score 与 kappa | 双人盲评 20 题、1~5 分 rubric，报告加权 kappa |
| 无 LLM 对照组 | 缺「同一 LLM + 不同上下文」的对比 | 接 `backend/app/llm/` 后补一组 |

## 10. 复现

```bash
# 全量：五组 x 3 次，结果写 var/eval/aggregate_*.json
python -m backend.app.eval.run_eval --all --repeat 3

# 单组
python -m backend.app.eval.run_eval --system rule
python -m backend.app.eval.run_eval --system agent_noreflect
python -m backend.app.eval.run_eval --system agent_norules

# 换题库
python -m backend.app.eval.run_eval --all --questions data/eval/questions.jsonl --limit 20
```

走 API 也可以：`POST /api/eval/run?system=agent_norules&limit=50`；
历史结果：`GET /api/eval/runs`。

无 Neo4j 时 `.env` 设 `KG_BACKEND=memory`，指标完全一致（同一份 `data/curated`），
只有时延会变成 6~13ms——这个差值本身就是「图数据库往返开销」的度量。
